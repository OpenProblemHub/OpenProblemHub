# Problem Review Checklist

This checklist is used by reviewers to evaluate whether a submitted problem
meets the quality bar of this community.

Reviewers should apply this checklist strictly.
If a submission fails any **critical** item, it should be rejected or returned
for revision.

This is not a judgment of the author.
It is a safeguard for problem quality.

---

## 1. Problem Reality Check (Critical)

- [ ] The problem describes a **real-world situation**, not a hypothetical scenario
- [ ] The author demonstrates **first-hand experience** or credible exposure
- [ ] The problem is currently happening, not a past or speculative issue
- [ ] The problem can be observed or independently verified

❌ Reject if the problem is abstract, speculative, or trend-driven.

---

## 2. Target User Clarity (Critical)

- [ ] The target user is a **specific role**, not a generic audience
- [ ] The user context (environment, scale, constraints) is clearly described
- [ ] The reviewer can clearly imagine a real person facing this problem

❌ Reject if the “user” is a market segment rather than an individual role.

---

## 3. Context & Constraints (Critical)

- [ ] Technical constraints are explicitly stated
- [ ] Organizational or process constraints are acknowledged
- [ ] Constraints meaningfully shape the problem

❌ Reject if the problem assumes an idealized or unconstrained environment.

---

## 4. Existing Solutions Analysis (Critical)

- [ ] Existing solutions or workarounds are acknowledged
- [ ] Their limitations are clearly explained
- [ ] The problem is not simply “the author hasn’t found the right tool”

❌ Reject if the problem reduces to tool discovery or preference.

---

## 5. Pain & Impact (Critical)

- [ ] The pain is concrete and specific
- [ ] Impact is measurable or observable
- [ ] The problem has real consequences if left unsolved

❌ Reject if the problem is merely inconvenient or subjective.

---

## 6. Why Now? (Important)

- [ ] There is a clear reason the problem is urgent or newly relevant
- [ ] The timing is justified by changes in technology, scale, or behavior

⚠️ Return for revision if “Why Now” is missing or weak.

---

## 7. Non-goals & Scope Control (Important)

- [ ] Non-goals are explicitly stated
- [ ] The scope is realistic and intentionally constrained
- [ ] The problem does not attempt to solve everything

⚠️ Return for revision if scope is ambiguous or overly broad.

---

## 8. Validation Signals (Critical)

- [ ] At least one credible validation signal is provided
- [ ] Signals go beyond personal opinion
- [ ] The problem is corroborated by external evidence or repeated experience

❌ Reject if no validation signals exist.

---

## 9. Engineering Worthiness (Critical)

- [ ] The problem is technically non-trivial
- [ ] Solving it requires engineering judgment, not configuration
- [ ] The solution space is likely to produce reusable patterns or systems

❌ Reject if the problem is primarily business, marketing, or UX opinion.

---

## 10. Open Questions Quality (Important)

- [ ] Open questions reveal genuine uncertainty
- [ ] Questions invite engineering exploration
- [ ] The author acknowledges unknowns

⚠️ Return for revision if open questions are missing or superficial.

---

## Final Decision

- [ ] **Accept** — Meets the community quality bar
- [ ] **Revise** — Promising but requires clarification or tightening
- [ ] **Reject** — Does not meet core criteria

---

## Reviewer Notes

- Focus on **problem quality**, not solution ideas
- Be explicit when rejecting; cite checklist items
- Consistency across reviews matters more than generosity
- Protect the long-term signal-to-noise ratio of the community

A strong rejection today prevents a weak standard tomorrow.
